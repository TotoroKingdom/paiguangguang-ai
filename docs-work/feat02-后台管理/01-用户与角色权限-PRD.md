> 版本：v0.2（已同步 2026-11-08 产品确认项）

> 建议归档：`docs-work/feat02-后台管理/01-用户与角色权限-PRD.md`

> 定义：**[确认]** 来自已确认产品讨论；**[建议]** 推荐默认值，待定稿；**[后续]** 不属于 V1。  
> 本文定义目标行为，**不表示现有功能已经实现**。

## 1. 目标、范围与成功标准

### 1.1 目标

建立统一账户体系，使游客、普通用户 User、能力开发者 Creator、管理员 Admin 使用同一身份登录平台；普通用户由管理员激活后获得正式使用权；所有管理入口可发现、所有资源按归属与权限隔离。

V1 最低成功标准：一个从未访问过网站的新用户能够完成**注册 → 得到数字账号 → 待激活登录 → 管理员从可见入口激活 → 用户登录 → 使用自己的工作台 → 再次登录恢复历史**，管理员能够完成角色配置和停用，并能通过审计回溯操作。

### 1.2 本期包含

- 无邮箱/手机的数字账号注册，唯一账号分配、注册成功提示、待审核流程。
- 数字账号 + 密码登录、会话续期/失效、退出、密码变更及重置流程。
- 统一 User / Creator / Admin 身份与最小 RBAC 及资源所有权检查。
- 管理员的用户审核、激活、拒绝、停用、恢复、角色调整、重置密码与审计。
- 管理控制台的显式入口及用户端、管理端双向切换。
- 私人数据按 `user_id` 归属；旧匿名浏览器会话的安全认领。
- 正式用户工作台与演示体验隔离。

### 1.3 不包含

邮箱、短信、社交登录、企业 SSO、自定义组织/租户、用户付费、复杂自定义角色编辑器、对用户私人聊天内容的后台全文检索。

## 2. 已确认的账号约束

| 编号 | 规则 | 状态 |
|---|---|---|
| ID-01 | 第一个普通注册账号为 `100`，之后每次成功注册递增 1 | [确认] |
| ID-02 | 无固定数量上限：`999 → 1000`，`9999 → 10000`，依次类推 | [确认] |
| ID-03 | 后端分配账号，不允许指定或修改登录账号 | [确认] |
| ID-04 | 不接入邮箱、短信、第三方身份服务 | [确认] |
| ID-05 | 登录为“数字账号 + 密码”，昵称可选 | [确认/建议] |
| ID-06 | 注册默认 `User + Pending`，由 Admin 激活方可使用正式服务 | [确认] |
| ID-07 | 内部主键与登录账号不同；账号唯一、不可回收复用 | [建议] |
| ID-08 | 首个 Admin 受信任初始化，不占普通自增序列；后续 Admin 由管理员授权 | [确认/建议] |

**账号与主键**：`account_number` 是展示/登录标识，内部资源归属统一使用稳定 `user_id`。不得将账号位数作为业务限制。分配必须是原子事务；一个成功注册只消耗一个唯一号码，失败事务不能出现两个用户拿到同一号码。注册重复提交需具备幂等或防重复策略。

## 3. 角色、状态与权限

### 3.1 角色

- Guest（未认证访问者）：仅访问网站、欢迎页、注册登录以及公开演示介绍；不是数据库角色。
- User：已激活后使用聊天、平台授权能力和本人数据；允许管理私人 Skill、本人 MCP 连接。
- Creator：继承 User 权限，允许创建和编辑本人负责的**平台能力草稿**、调试、提交审核；不能越权发布。
- Admin：继承 User 权限，负责用户审核、角色授权、能力发布、系统配置和全局运行元数据审计。

[建议] V1 使用三个固定已登录角色，不做可视化角色设计器；权限应由服务端以明确权限点判断。**Admin 不因角色拥有读取用户私有聊天正文、文件内容、凭据明文的默认权限。**

### 3.2 账户状态（与角色正交）

| 状态 | 用户可做什么 | 允许的操作 |
|---|---|---|
| `PENDING` | 验证凭据后查看审核状态、退出 | 查询本人审核状态 |
| `ACTIVE` | 按角色使用用户端或授权管理功能 | 正式聊天、能力执行等 |
| `DISABLED` | 看到停用提示，不能使用正式服务 | 退出及受控申诉/联系管理员说明 |
| `REJECTED` | 看到申请未通过提示 | 退出；是否再次申请由后台策略决定 |

状态流转：`注册 → PENDING → ACTIVE`；`PENDING → REJECTED`；`ACTIVE ↔ DISABLED`。拒绝与停用必须有审计理由。被停用用户现存会话应失效；已有数据保留策略单独定义，**停用不等于删除**。

### 3.3 核心权限矩阵

| 权限点 | User | Creator | Admin |
|---|:---:|:---:|:---:|
| 查看/修改本人资料、本人会话和文件 | ✓ | ✓ | ✓ |
| 使用已授权平台能力 | ✓ | ✓ | ✓ |
| 创建/管理本人私人 Skill、MCP 连接 | ✓ | ✓ | ✓ |
| 创建/编辑本人负责的平台能力草稿 | — | ✓ | ✓ |
| 编辑他人的平台草稿 | — | — | ✓ |
| 提交平台能力审核 | — | ✓ | ✓ |
| 审核、发布、停用、回滚平台能力 | — | — | ✓ |
| 查看自己发起的 Run | ✓ | ✓ | ✓ |
| 查看本人负责的能力运行汇总 | — | ✓ | ✓ |
| 查看全局运行元数据和审计 | — | — | ✓ |
| 激活用户、调整角色、重置密码 | — | — | ✓ |
| 调整系统注册/默认授权政策 | — | — | ✓ |

资源级权限还必须校验所有权或明确授权：角色允许“编辑能力”不等于可编辑所有 Creator 的资源。

## 4. 用户端流程与交互契约

### 4.1 入口与路由

| URL | 访问前提 | 页面行为 |
|---|---|---|
| `/assistant` | 任何人 | 游客欢迎；Active 进入工作台；Pending 转状态页 |
| `/assistant/register` | 游客 | 注册表单：密码、确认密码、可选昵称 |
| `/assistant/register/success` | 刚注册成功 | 仅本次注册流程展示**真实账号**及保存提示 |
| `/assistant/login` | 游客 | 数字账号、密码、登录；支持合法 `returnTo` |
| `/assistant/pending` | Pending | 等待激活、刷新状态、退出登录 |
| `/assistant/me` | Active | 资料、安全、我的资源、会话与使用记录 |
| `/assistant/chat/:id` | Active 且所有权符合 | 仅访问本人聊天 |
| `/assistant/admin` | Admin；Creator 有限管理权限 | 按管理角色显示许可页面，其他人拒绝 |
| `/assistant/admin/users` | Admin | 用户列表与注册审核 |
| `/assistant/admin/roles` | Admin | 角色授权与权限矩阵 |

直接访问任何受保护 URL 时，后端作权限终裁；前端导航只是辅助。登录后的重定向只能指向站内批准的路径，不能形成开放重定向。

### 4.2 注册

1. 用户填写密码/确认密码，昵称可选；前端校验后提交。
2. 服务端进行注册限流和校验，以事务方式分配下一个可用数字账号并创建 `User/PENDING`。
3. 返回真实账号及注册结果；成功页提供复制账号和**必须保存账号**的提示。
4. 成功后允许用户持凭据登录并查看 Pending 页面，但不得访问正式工作台或执行 AI 请求。
5. 重复点击、网络重试不得静默创建多份账号；失败必须可理解并可重试。

[建议] 注册限流按来源、时间窗口、设备信号组合进行，必要时增加人机校验，防止无上限递增账号被恶意刷号。前端不得预计算下一个账号。

### 4.3 登录

1. 输入数字账号和密码；空值、非法数字账号、错误密码等提供安全且一致的错误响应。
2. 凭据正确：`ACTIVE` 进入工作台；`PENDING` 进入待审核页；`DISABLED/REJECTED` 显示相应状态且不签发可访问正式 API 的权限。
3. 页面顶部账户菜单显示账号与昵称、个人中心、退出登录；有管理权限时另外显示管理入口。
4. 管理页面提供**返回用户工作台**；无需单独的管理员密码体系或重复登录。

### 4.4 待激活与管理员审核

- Pending 页面显示账号及状态、刷新审核结果、退出登录；不显示正式能力目录。
- 管理员总览显示待激活人数；用户管理支持搜索账号、按状态筛选、查看详情、激活/拒绝。
- 审核决策记录操作者、时间、理由、前后状态；用户刷新后看到最新状态。
- 同一请求重复激活或重复拒绝不得产生不一致状态；如状态变化竞争，提示冲突并刷新。

### 4.5 密码与无第三方找回

[已确认] 密码最少 **6 位**。因数字账号可枚举，必须结合登录限流、分级延迟、会话吊销、常见弱密码拒绝及异常告警；不允许擅自提高产品最低长度。

[已确认] 使用**一次性恢复码 + 管理员辅助**。注册成功时发放恢复码，仅向用户展示一次，服务端仅保存哈希；用户遗失密码时可通过未使用的恢复码重设，成功后旧恢复码作废、生成新码并撤销旧会话。管理员辅助重置必须经过可信线下身份核验；如果无法验证归属，**不能仅凭账号数字直接重设密码**。具体核验 SOP 与凭证交付方式仍待安全运维细化。

### 4.6 管理员入口可发现

- `Guest`：欢迎页及网站入口清楚显示登录/注册。
- `User`：顶部头像菜单和个人中心显示个人资料与安全设置，不显示后台。
- `Creator`：头像菜单显示“能力创作中心”；点击后进入有权限的管理模块。
- `Admin`：头像菜单与个人中心显示“管理控制台”；登录成功若来自后台入口则返回管理首页。
- 管理端固定显示“返回用户工作台”。
- 角色变化以服务端权限为准；前端权限缓存需及时刷新。知道后台 URL 也不能绕过权限。

## 5. 个人资源、旧会话与迁移

### 5.1 数据归属

会话、消息、文件、个人 Skill、收藏、个人 MCP 连接、个人运行记录和用户设置均以稳定 `user_id` 关联。访问和删除按所有权检查；跨浏览器登录后取得**同一账号**数据，不能根据浏览器 Cookie 隔离成新用户。

### 5.2 现有身份迁移

当前系统同时存在 `admin_users/admin_sessions` 和匿名浏览器 Owner Cookie。目标是统一用户模型，而不是让管理员和普通用户保留两套账户。建议采取迁移/兼容阶段：

1. 受信任初始化或迁移既有管理员至统一用户身份；保留安全回退路径；**绝不可将现有明文凭据写进迁移脚本**。
2. 旧匿名会话维持可读一段迁移期；用户登录后主动点击“认领此浏览器的历史记录”。
3. 服务端验证当前浏览器的**匿名 Owner Cookie** 对旧会话的合法控制权，展示可迁移条目数及影响，再执行幂等归属转移。
4. 不自动将其他设备、其他匿名浏览器或已属于其他用户的会话绑定到当前账号；合并冲突有明确结果和审计。
5. 完成验收后逐步下线匿名写入路径，不直接删除用户历史。

## 6. 安全与运营约束

- 生产必须使用 HTTPS；HttpOnly、Secure、SameSite Cookie 与 CSRF/Origin 防护适用于有状态管理操作。
- 密码采用可靠自适应哈希，不保存明文；密钥、会话 Token 和恢复码不写日志。
- 注册与登录限流；数字账号可推测，公开接口不得提供批量账号有效性探测。
- 后台用户列表限制 Admin，包含分页、筛选及审计；Creator 不得通过 ID 枚举用户。
- 禁止修改/停用系统内最后一个可用 Admin；敏感角色变更需要审计与必要的二次确认。
- 账号停用后立即拒绝新请求及后续工具调用，并吊销现有会话；运行中任务在权限边界检查处停止。
- 账号注册与正式模型调用分别受限流、配额与预算控制。

## 7. 端到端验收（V1 门槛）

| 编号 | 场景 | 可验证结果 |
|---|---|---|
| A01 | 顺序注册 | 注册连续获得 `100、101、102`（在新空库），内部 ID 不等于展示账号 |
| A02 | 跨位数 | `999 → 1000`、`9999 → 10000` 正确，无号段上限 |
| A03 | 并发与重试 | 并发注册账号不重复；网络重试不无故生成多份账号 |
| A04 | 待审核 | 正确凭据可查看 Pending 状态，正式聊天及运行 API 拒绝 |
| A05 | 审核 | Admin 在可见页面激活账号，用户刷新后可使用 |
| A06 | 状态禁止 | 停用/拒绝账户无法访问正式 API；停用立即使旧会话失效 |
| A07 | 角色 | User 不得访问管理 API；Creator 只能操作自己的能力；Admin 可授权 |
| A08 | 入口 | Admin/Creator 通过头像菜单进入管理模块，后台可返回工作台 |
| A09 | 归属 | A 用户无法访问 B 的聊天/文件/Skill/MCP 凭据及 Run |
| A10 | 跨浏览器 | 同一用户在另一浏览器登录恢复本人会话与个人资源 |
| A11 | 旧会话认领 | 仅合法匿名会话持有者能选择认领，重复执行幂等 |
| A12 | 安全 | 登录暴力尝试触发限制；密码恢复未授权无法进行；最后管理员不能被停用 |

## 8. 待定稿决策（不应暗自当作确认需求）

1. **密码强度 [已确认]**：最低 6 字符；登录限流、常见弱密码拒绝、重置限流等属于配套安全要求，具体阈值待安全规格确认。
2. **找回机制 [已确认]**：一次性恢复码 + 管理员辅助；恢复码发放数量、人工核验 SOP、交付渠道仍待细化。
3. **注册治理**：默认完全开放注册+管理员激活，还是增加邀请开关与风险校验；建议后台可配置开关。
4. **拒绝后的处理**：拒绝用户是否允许重新提交审核，何时清理其最少必要信息。
5. **Creator 后台入口**：使用 `/assistant/admin` 的权限过滤界面，或单独 `/assistant/creator`；建议 V1 共用后台布局、按权限渲染菜单。

## 9. 验收与实施顺序约束

产品规格确认后再拆技术任务。先做统一身份及真实权限判定，再启用后台用户管理和入口；随后迁移个人资源与旧匿名会话。避免只做登录页、但用户会话仍依赖匿名 Cookie 的“假登录”状态。

**出阶段条件：A01–A12 达到验收要求；无需实现真实 Agent Runtime，但不能伪造正式能力执行状态。**

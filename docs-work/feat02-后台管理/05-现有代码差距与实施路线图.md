## 0. 执行摘要

**整体判定：产品 V1 未闭环，现有工程具有可复用基础；应采用渐进迁移，而非推倒重建。**

1. **有基础**：FastAPI + SQLAlchemy/Alembic + SQLite，会话/消息持久化与匿名 Owner Cookie，管理员专用登录、管理页面，Tool/Skill/MCP/Agent 通用能力目录、草稿/版本/发布/停用、原子化发布与审计的代码及相关测试。
2. **关键缺口**：没有普通用户数字账号的注册与统一登录；没有 Pending 激活、User/Creator/Admin 真正的权限及管理 UI；聊天、文件、个人 Skill/MCP 连接尚未归属于同一 `user_id`。
3. **真实性缺口**：启动时将内置 Demo 能力写成已发布；前端模拟对话与 MCP 连接；运行记录为 `accepted` 而不是实际完成；无真实 LLM/Tool/MCP/Agent Runtime。
4. **上线阻断**：PR [#11](https://github.com/TotoroKingdom/paiguangguang-ai/pull/11) 仍处于 Open/Draft/BLOCKED，涉及 HTTPS/443、密钥与 Origin、部署权限及依赖安全风险；必须在发布前重新实测核对。
5. **建议路径**：G0 安全规则与迁移方案冻结 → G1 统一身份/归属 → G2 能力权限与连接授权 → G3 真实执行 → G4 生产与全量验收。**每阶段都有独立验收门禁，不将页面完成等同于产品完成。**

## 3. 关键冲突与风险（应优先处理）

### RISK-01：管理员已经“可登录”，但不是统一账户

`frontend/src/features/assistant/assistant-workspace.tsx` 会调用 `getAdminSession()`，只有取得独立 Admin Cookie 后才显示“管理控制台”。因此“没有后台入口”的用户感知与源码并不矛盾：**首次进入工作台/正常用户登录流无法发现如何取得这套 Admin Cookie**。修复应是“统一登录 + 权限菜单”，而不是单独多加一个固定 Admin 按钮。

### RISK-02：匿名 Owner 与用户 ID 不能直接合并

现有 `owner_id` 是浏览器 Cookie 身份，不是经过账户认证的用户。直接把 `owner_id` 字段重命名为 `user_id` 或用登录账号覆盖，可能导致数据串户、旧历史失联、匿名所有权错误。应采用**新字段/新关联 + 显式认领 + 校验/迁移 + 安全收口**。

### RISK-03：前端“个人 Skill 已导入”不代表后端“允许调用”

`getCapabilities()` 合并本地 `userSkills`，用户可把 Skill 选到聊天请求；`create_turn` 服务端却调用 `resolve_published` 只识别平台已发布的能力 ID。静态逻辑显示存在**潜在 422 不一致**；必须 E2E 复现后修复，不能仅改前端提示文案。

### RISK-04：MCP 自定义 URL 与已确认产品规则相冲突

当前用户端还保留“连接地址”输入框和 `testConnection` 模拟实现。已确认的 V1 是 **User 只能连接管理员批准的 MCP Server**；允许客户端任意 URL 直接连真实 Runtime 会形成 SSRF/内部网访问风险。平台审批、白名单、服务端连接校验与个人授权必须拆开。

### RISK-05：已发布 Demo 与真实运行混淆

`ensure_demo_catalog()` 无条件初始化，Demo 能力为 Published；`provider.tsx` 仍调用 `createMockReply`。这允许“目录能选择、API 接受、UI 有回复”，但没有实际 LLM/工具执行。验收必须将 **Catalog Published / Authorized / Ready / Run Completed** 四个状态分别验证。

### RISK-06：密码最低 6 位与现有管理员密码函数的差异

产品规则“普通用户密码至少 6 位”已确定，不应被后端 `hash_password()` 现有“管理员密码至少 12 位”自动覆盖。建议把**密码哈希算法**和**按账户类型/初始化流程执行的密码策略**分开；不降低恢复码熵与管理员初始化安全策略。6 位弱密码需配合常见弱口令拒绝、共享限流、异常登录保护。

### RISK-07：管理员恢复流程和首次初始化是安全阻断

没有可信的人工身份核验方案时，“仅凭账号的后台重置密码”可能造成账户接管。初始化不能让未知外部用户成为首个 Admin；也不能因重启而意外覆盖管理员改过的密码。应先冻结 SOP，再开放重置 UI。

### RISK-08：发布与部署条件不等同于代码合并

当前生产发布 PR #11 仍 Draft/BLOCKED，具体阻断**按 PR 的历史自述**包括 TLS、密钥/Origin、部署授权以及依赖安全扫描；这些不能因 CI 通过而视为解决。上线前需要再次核验当前服务器与完整部署链。

## 4. 目标增量架构（推荐）

```mermaid
flowchart TD
    Visitor[游客] --> Entry[/assistant 统一入口]
    Entry --> Auth[统一认证与账户状态]
    Auth --> UserUI[用户工作台]
    Auth --> AdminUI[Creator/Admin 管理界面]
    Auth --> Users[(Users / Sessions / Recovery Codes)]
    UserUI --> ResourceAPI[资源目录 + ACL + 所有权]
    AdminUI --> ResourceAPI
    ResourceAPI --> CapabilityDB[(能力 / 版本 / 审核 / 授权)]
    UserUI --> Runtime[AI Runtime / Run]
    Runtime --> Model[LLM Provider]
    Runtime --> Tool[Tool Gateway]
    Tool --> MCP[MCP Client - 批准 Server]
    Runtime --> Runs[(Run / Steps / Trace)]
    UserUI --> Personal[(个人会话 / 文件 / Skill / Connection)]
    Legacy[旧匿名 Owner Cookie] --> Claim[显式历史认领]
    Claim --> Personal
```

### 4.1 数据领域边界

| 目标领域 | 建议新增/调整实体 | 迁移原则 |
|---|---|---|
| 身份 | `users`（内部 UUID、数字登录号、昵称、密码摘要、状态）、`user_sessions`、`user_recovery_codes`、账号序列/幂等记录 | 登录账号展示为**字符串**，不能限制三位；序列数据库原子维护、唯一约束 |
| 角色授权 | 简单 `user_roles`、必要的 `resource_permissions` 或显式授权记录 | V1 内置 User/Creator/Admin，不急于做复杂权限编辑器 |
| 聊天所有权 | `conversations.user_id` 可空过渡、原 `owner_id` 保留认领窗口 | 不直接覆盖旧字段；所有查询按已认证身份/合法旧会话界定 |
| 个人资源 | 个人 `skills`、`files`、`mcp_connections` 的 Owner/FK | 私人资源默认仅本人可见；外部 Token 仅服务端密文或安全凭据引用 |
| 能力治理 | 能力版本、审核/发布记录、ACL、依赖版本锁定、Ready 状态 | 复用现有 Definition/Version/Dependency，增量迁移而非清表 |
| 执行 | `runs`、`run_steps`、状态/错误/耗时/关联消息；真实模型调用 | `accepted` 为准入而非终态；模拟 Runs 与正式 Runs 明确分开 |

### 4.2 账号分配实现约束

- 注册从 `100` 起连续递增，跨三位/四位/五位；注册操作**在服务端**完成，API、Cookie、前端表单均不假设固定长度。
- 账号分配使用数据库事务和唯一约束，避免并发重复；支持幂等键或等效的注册重试恢复。拒绝/停用/删除的账号不重用。
- 不把账号上限设为 `999`；但底层 SQLite 的整数范围仍是物理技术约束。未来扩容方案可以将用户可见账号和计数存为高精度数值字符串，不能承诺底层机器具备数学意义上的无限容量。
- `users.id` 与账号号段分离，避免后续迁移时修改所有资源主键。

### 4.3 旧系统渐进迁移（建议按顺序实施）

1. **Preflight**：备份数据库、记录 migration revision/当前 `admin_users` 与匿名会话统计，建立只读核验与回滚步骤；不在真实生产直接演练删除。
2. **Expand**：新增统一 Users/Sessions/Recovery 等表；会话添加可空 `user_id` 或安全归属映射；旧接口仍可用于过渡和历史认领；确保旧表/旧数据不被自动清理。
3. **Bridge**：将现有 Admin 通过受信任一次性迁移流程映射到统一 Users，先验证新登录与 Admin 权限，再逐步停用旧 Admin 登录；保留有限期故障回滚路径。
4. **Claim**：用户登录后明确选择认领旧匿名会话；同时验证旧签名 Owner Cookie、当前 User 身份和操作防重放；原子批量迁移且幂等。其他用户不能认领。
5. **Switch**：正式会话和个人资源只接受统一身份；能力目录/执行网关用新的 RBAC + Owner 校验，旧 Owner 仅在受控迁移端点使用。
6. **Contract**：完成 U-12～U-15、O-05 的验证并取得备份恢复证据后，才考虑删除旧字段、旧 Admin Cookie 和演示兼容逻辑。

**不要双重权威源**：过渡期可以兼容读取/显式迁移，但不能让匿名 Owner 与登录 User 同时无约束写同一正式私人资源。

### 5.1 推荐先交付的最小垂直切片

**切片 S1：数字账号注册 → 待激活 → 管理员从可发现入口激活 → 统一账号登录 → 创建聊天 → 换浏览器登录可恢复。**

这是首次真正产品闭环，交付时还应覆盖“普通用户不能进入后台”及“管理员停用后会话立即失效”。此时可以继续明确标注“AI 执行未接入”，**不能声称平台完整 V1 已通过**。

**切片 S2：Creator 创建 Tool 草稿 → Admin 审核/发布 → 受授权用户可见/可调用，未授权用户不可调用。** 为避免假通过，需要有真实只读测试 Tool，不能只保存 Schema。

**切片 S3：管理员批准 MCP Server → 用户授权个人 Connection → 选择 Agent → 真实模型调用 Tool/MCP → 产生可复查 Run。**

### 5.2 可以并行与必须串行的部分

- **可并行**：注册/登录 UI 原型与后端 Users/API 契约设计；后台用户列表 UI 与权限 API；LLM Provider 的独立接口原型与 Tool 测试夹具（可先做只读，**不得在未接权限时上线**）。
- **必须串行或设置门禁**：用户数据认领依赖稳定 Users 与会话归属模型；用户可调用能力依赖服务端 ACL；真实 MCP 执行依赖批准 Server 与个人授权；生产发布依赖安全和回滚证据。
- **避免冲突**：不同工作分支/执行 Agent 不应并行修改 `provider.tsx`、`main.py`、核心认证依赖或同一迁移文件；先冻结 API 契约，再让前后端分别实现。

## 6. 下一份 `06-实施TASKS.md` 应采用的任务卡格式

**不要把 G1～G4 直接交给 Codex 作为一个巨大任务。** 每张任务卡必须包含：

任务卡应该保证**每次合并后的 `dev` 仍可运行且没有演示伪成功**。对于原功能模拟行为，可保留清晰标记的测试环境入口，但不得以“降级到 Mock”掩盖生产故障。

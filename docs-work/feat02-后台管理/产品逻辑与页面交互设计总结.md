# 智能助手平台 V1
> 产品逻辑与页面交互设计总结｜讨论稿 v0.3

> 编制日期：2026-11-08｜状态：产品讨论稿（非实施完成声明）

依据前几轮产品讨论整理；以最新确定的数字账号注册方案为准。本文用于统一业务认知和下一轮 PRD 设计，不代表开发已经完成。

## 01  产品定位与架构边界

产品目标：从个人网站中的“智能助手展示页面”，升级为具有真实用户体系、角色权限、能力管理、AI 执行与运行治理的独立应用模块。

| 产品面 | 定位 | 建议入口 |
| --- | --- | --- |
| 个人网站 | 作品、RAG、3D 实验室及智能助手展示入口 | / |
| 用户工作台 | 聊天、能力发现与使用、个人文件、个人配置、历史记录 | /assistant |
| 管理控制台 | 用户审核、角色授权、能力治理、发布、运行监控、系统设置 | /assistant/admin |
| 后端能力平台 | 统一身份、资源管理、权限校验、AI Runtime 与审计 | FastAPI /api/v1 |

> **说明：** 工程边界：现阶段继续采用同仓库、同部署、产品逻辑隔离；暂不拆分独立仓库、域名或微服务。未来可以演进为独立部署。

> **流程：** 个人网站 → 智能助手入口 → 统一认证/账户状态 → 用户工作台 或 管理控制台 → AI Runtime / 资源管理

## 02  注册、账号与登录机制（最新已确认方案）

### 2.1  数字账号分配

| 规则 | 设计                                     |
| --- |----------------------------------------|
| 账号形式 | 三位数字账号，从 100 开始：100、101、102……          |
| 生成方式 | 后端在注册成功时自动分配；新注册账号在前一个号段基础上 +1，不允许自行选择 |
| 账号上限 | 不设上限额，三位数字满了，就4位数，4位数满了就5位数；以此类推       |
| 用户注册信息 | 密码、确认密码；昵称可选（建议）                       |
| 不接入的能力 | 不使用邮箱注册、邮箱验证码、短信或第三方身份服务               |
| 初始角色与状态 | 默认 User、Pending（待管理员激活）                |
| 登录方式 | 数字账号 + 密码                              |
| 账号回收 | 建议已分配账号不复用，避免身份混淆                      |

数据库内部用户主键应与展示的登录账号分离；分配操作需唯一约束和事务/原子计数，防止并发注册获得相同账号。

### 2.2  从注册到使用的完整路径

> **流程：** 游客进入 /assistant → 点击注册 → 填写密码、确认密码 → 服务端分配数字账号 → 注册成功页显示账号并提醒保存 → Pending → 管理员后台激活 → Active → 数字账号和密码登录 → 正式用户工作台

- 注册成功页显示真实分配的账号，提供“复制账号”和保存提醒；不再展示伪造的固定 100。
- 待激活用户可以验证登录凭据并查看审核状态，但不能创建正式 AI 运行、使用能力或访问正式聊天工作台。
- 管理员在后台激活后，用户刷新状态并进入工作台；不依赖邮件或短信通知。
- 账号停用后，已有会话应失效；账号拒绝、登录错误和密码重置都有明确的提示与安全控制。
### 2.3  管理员身份

管理员和普通用户应归属于同一身份体系：同一账户既能进入用户工作台，具有权限时也能进入管理控制台。首个管理员通过受信任的初始化流程创建；后续管理员由已有管理员授予权限。当前代码中独立 admin_users 及匿名浏览器身份需要规划平滑迁移。

> **说明：** 建议：管理初始化账户可使用保留管理员标识，不占普通用户 100～999 号段；具体后台初始化方式留给技术设计。禁止公开注册用户自行选择 Admin。

## 03  用户角色、账户状态与权限

### 3.1  角色及职责

| 访问主体 | 定位 | 可做什么 |
| --- | --- | --- |
| 游客 Guest | 未登录访问者 | 查看个人网站、产品介绍与明确标注的预览 |
| 普通用户 User | 已激活平台用户 | 聊天、使用获授权能力、管理个人历史/文件/Skill/MCP 授权 |
| 能力开发者 Creator | 具有创作权限的用户 | 具备 User 权限，可开发和调试负责的能力、提交发布申请 |
| 管理员 Admin | 平台治理角色 | 审核用户、分配角色、管理发布、模型与平台资源、审计与系统设置 |

“角色”与“账户状态”必须分离：用户状态可包含 Pending / Active / Disabled / Rejected；角色决定操作类别，资源级权限决定可操作的具体对象。

### 3.2  权限矩阵（V1 建议基线）

| 操作 | User | Creator | Admin |
| --- | --- | --- | --- |
| AI 聊天与个人资源管理 | ✓ | ✓ | ✓ |
| 使用已授权的平台能力 | ✓ | ✓ | ✓ |
| 创建/导入个人 Skill、维护个人 MCP 授权 | ✓ | ✓ | ✓ |
| 创建平台 Tool / Agent 草稿 | — | ✓ | ✓ |
| 编辑他人的平台草稿 | — | — | ✓ |
| 提交能力审核 | — | ✓ | ✓ |
| 审批发布/停用/回滚能力 | — | — | ✓ |
| 查看个人运行记录 | ✓ | ✓ | ✓ |
| 查看平台运行与管理审计 | — | 限自身/授权范围 | ✓ |
| 审核用户、调整角色、系统策略 | — | — | ✓ |

管理员可以治理账号与权限，但不默认具有读取用户私人聊天正文、私有文件或第三方凭据明文的能力。个人隐私数据的运维访问需明确授权、最小范围和审计。

### 3.3  用户状态流转

> **流程：** 注册 → Pending（等待激活） → 管理员激活 → Active（允许正式使用） → 管理员停用 → Disabled；管理员可恢复 Active。待审核申请也可被拒绝 Rejected。

## 04  页面信息架构与访问规则

关键原则：/assistant 是统一入口；未登录展示欢迎/登录注册引导，待激活展示审核状态，已激活用户展示聊天工作台。访问限制由服务端最终判定。

| URL | 页面 | 访问主体/行为 |
| --- | --- | --- |
| /assistant | 统一入口 | 游客欢迎页；已激活用户进入工作台；待激活进入状态页 |
| /assistant/login | 登录 | 游客输入数字账号 + 密码；支持登录后返回原目标页 |
| /assistant/register | 注册 | 游客申请账号 |
| /assistant/register/success | 注册成功 | 显示分配账号，仅在本次注册流程中可见 |
| /assistant/pending | 审核状态 | 待激活用户查看状态、刷新状态、退出登录 |
| /assistant/chat/[id] | 聊天详情 | Active 用户、仅本人会话 |
| /assistant/tools /skills /mcp /agents | 能力目录 | Active 用户；按权限过滤 |
| /assistant/files | 文件库 | Active 用户，个人数据隔离 |
| /assistant/me | 个人中心 | Active 用户查看账户、个人能力、连接和使用记录 |
| /assistant/admin | 管理首页 | Admin；Creator 仅访问获授权的管理模块 |
| /assistant/admin/users | 用户管理/注册审核 | Admin |
| /assistant/admin/roles | 角色与授权 | Admin |

### 4.1  后台入口必须可发现

- 未登录：智能助手入口及欢迎页清晰展示“登录 / 注册”。
- 已登录管理员：顶部头像菜单与个人中心都显示“管理控制台”；可直接进入 /assistant/admin。
- Creator：显示“能力创作中心”或对应的有限管理入口，不展示无权模块。
- 管理后台顶部：固定“返回用户工作台”入口，形成双向切换。
- 普通用户：没有管理导航；即使手动输入管理 URL，页面及 API 仍必须拒绝越权。
### 4.2  个人中心最小信息架构

| 页面 | 主要内容 |
| --- | --- |
| 个人资料 | 数字账号、昵称、账户状态及基础资料 |
| 账户安全 | 修改密码、退出登录、会话管理；无邮箱找回，管理员辅助重置 |
| 我的能力 | 已启用、已授权和收藏的能力 |
| 我的技能 | 个人 Skill 的创建、导入、编辑与删除 |
| 我的连接 | MCP 连接、OAuth/凭据授权状态、断开授权 |
| 我的文件 | 个人文件管理及容量状态 |
| 使用记录 | 聊天历史、运行历史、配额/调用统计与反馈 |

## 05  管理控制台 V1 的完整职责

| 一级模块 | 二级内容 | 业务目标 |
| --- | --- | --- |
| 平台总览 | 用户规模、待审核、能力数、运行情况 | 了解平台当前状态与异常 |
| 用户与权限 | 用户列表、待激活、用户详情、角色、停用/恢复 | 管理谁能进入及能做什么 |
| AI 资源管理 | 模型供应商、密钥引用、配额策略 | 控制平台基础资源 |
| 能力中心 | Tool / Skill / MCP / Agent 的创建、配置与调试 | 管理 AI 资源供给 |
| 发布中心 | 审核、不可变版本、发布、停用、回滚 | 控制线上能力变更 |
| 运行中心 | Run、Trace、错误、审计、用户反馈 | 定位问题并持续优化 |
| 系统设置 | 注册策略、安全策略、默认权限 | 治理平台行为 |

### 5.1  管理员的三条主要业务线

> **流程：** 用户治理：注册申请 → 待激活列表 → 管理员审核/激活 → 赋予 User / Creator / Admin → 管理状态与权限

> **流程：** 能力治理：Creator 创建草稿 → 配置与调试 → 提交审核 → Admin 发布 → 用户发现、授权、使用 → 版本更新/停用

> **流程：** 运行治理：用户请求 → 服务端鉴权与执行 → Run / Trace / 错误记录 → 管理端观察与反馈 → 能力优化

## 06  Tool / Skill / MCP / Agent 的产品模型

| 能力类型 | 平台侧职责 | 用户侧职责 |
| --- | --- | --- |
| Tool | 定义执行方式、参数 Schema、权限、超时、发布版本 | 发现并调用有权使用的工具 |
| Skill | 维护指令、资源、依赖、验证与版本 | 使用平台 Skill；创建个人 Skill |
| MCP | 注册 MCP Server、连接策略、工具发现、权限控制 | 用自己的身份授权外部连接并使用工具 |
| Agent | 配置模型、提示词、Tool/Skill/MCP 依赖、发布 | 选择智能体并执行任务、查看历史 |

### 6.1  四个相互独立的资源维度

| 维度 | 示例 | 说明 |
| --- | --- | --- |
| 资源所有权 | 平台 / 用户个人 | 谁维护及承担管理职责 |
| 发布状态 | Draft / Review / Published / Disabled | 是否进入上线生命周期 |
| 可见范围 | 公开预览 / 已登录 / 指定角色 / 私有 | 谁能发现它 |
| 使用权限与授权 | 可执行 / 需授权 / 禁止 / 需审批 | 谁能真正调用它 |

还需独立的“运行就绪状态”：已发布不等于可执行；模型、Tool Executor 或 MCP 服务尚未连接时，必须清楚标注不可用，不能伪装成正常功能。

### 6.2  资源归属与安全

- 平台 Skill、Tool、MCP Server 和 Agent 由 Creator / Admin 按权限开发、发布和维护。
- 个人 Skill 和用户上传文件默认只对本人可见；不得因管理员拥有平台治理权限就自动公开。
- MCP Server 注册是平台行为，用户的外部账号授权是个人行为；不得共享管理员或其他用户的凭据。
- Agent 发布版本应固定依赖的具体能力版本；执行时再次校验依赖的状态、用户权限和外部授权。
### 6.3  演示能力与真实能力隔离

现有系统存在已发布的内置演示资源及浏览器模拟回复。正式用户目录只展示真实可执行能力、需授权能力和清晰标明不可用的项目；演示数据放入独立 Demo / 示例区，或仅用于开发测试环境。

## 07  两条闭环：产品业务与 AI 执行

### 7.1  业务闭环

> **流程：** 注册/登录 → 账户激活 → 进入工作台 → 按身份过滤能力目录 → 启用或授权 → 执行请求 → 查看历史/反馈 → 管理后台治理与迭代

### 7.2  执行闭环

> **流程：** 用户请求 → 身份、权限与配额校验 → 解析并固定能力及依赖版本 → Agent Runtime 调用 LLM / Tool / MCP / Skill → 返回真实结果 → 持久化执行状态/日志 → 监控与评测

两条闭环缺一不可：只有管理后台没有真实 Runtime，只是管理原型；只有 Runtime 没有账户和授权，也只是聊天 Demo。

### 7.3  关键状态与故障处理

| 对象 | 主要状态/异常 | 产品行为 |
| --- | --- | --- |
| 用户账户 | Pending / Active / Disabled / Rejected | 未激活不可执行；停用使会话和新调用失效 |
| MCP 连接 | 未连接 / 待授权 / 已连接 / 过期 / 失败 | 引导授权或重连，不回退模拟执行 |
| 能力版本 | 草稿 / 待审核 / 发布 / 退役 | 历史可查；新运行按当前发布版本校验 |
| 运行 Run | 排队 / 执行 / 等待授权或审批 / 成功 / 失败 / 取消 / 超时 | 显示真实状态、错误与可追踪记录 |

## 08  与当前仓库实现的差距（已核对的阶段性事实）

此前只读检查基于仓库 TotoroKingdom/paiguangguang-ai 的 dev 分支，时间为 2026-11-08。该段是实现状态快照，不代表未来代码仍相同。

| 现有实现 | V1 目标差距 |
| --- | --- |
| 管理控制台基础页面与独立路由布局已完成 | 缺少可操作的用户注册、统一用户身份、角色授权后台 |
| 独立管理员登录 admin_users / admin_sessions | 需与普通用户统一身份、角色和登录入口 |
| 匿名 Cookie 实现浏览器会话隔离 | 需升级为用户归属，并安全认领旧匿名历史 |
| 平台能力 CRUD、草稿版本、发布/停用与审计已实现 | 能力发布与授权、可见范围、真实可执行状态尚未完整闭环 |
| 目录初始包含 24 个演示能力，浏览器端模拟生成回复 | 需严格隔离演示资源并建设真实 Runtime |
| 后台有 capability_runs 准入记录 | 还不是 LLM/Tool/Agent 的真实执行 Trace |
| dev 分支功能已合并并通过原阶段 CI | 此前生产 main 发布受 HTTPS、密钥、依赖风险等事项阻塞 |

> **说明：** 优先级发生变化：下一步不应直接大规模扩展 Agent Runtime，而应先完成产品身份/权限与 UI 入口闭环，解决演示数据归属问题，然后分阶段接真实执行。

## 09  V1 端到端验收场景

| 场景 | 必须得到的结果 |
| --- | --- |
| 游客发现产品 | 从个人网站进入智能助手；清晰找到登录、注册和产品介绍 |
| 数字账号注册 | 连续注册分配 100、101…；并发无重复，成功页提供保存提醒 |
| 后台审核激活 | 新账号默认为 Pending；管理员可激活或拒绝；激活状态立即生效 |
| 登录与权限隔离 | Active 用户可用；Pending/Disabled 不可调用；普通用户无法越权管理 |
| 管理员入口 | Admin/Creator 有明确可见的管理入口；工作台与后台可双向切换 |
| 角色授权 | 管理员能赋予 Creator 并限制能力管理范围；非管理员不可自我提权 |
| 个人数据与迁移 | 跨浏览器登录访问本人数据；旧匿名历史可安全选择认领 |
| 能力发布与访问控制 | 发布后按角色/授权可见；未授权不可执行；停用后新调用被拒绝 |
| 真实 AI 执行 | 至少一个 Agent 完成真实模型和工具调用，产生可追踪结果 |
| 运行治理 | 用户查看历史与反馈；管理员查看对应运行状态、耗时、错误和审计 |

## 10  下一轮规划与尚待敲定事项

### 10.1  建议产品设计顺序

- 第 1 项：数字账号注册/登录/激活/停用的详细 PRD、页面状态和安全规则。
- 第 2 项：统一用户模型、个人资源归属、旧匿名会话认领及角色授权方案。
- 第 3 项：四类能力的创建、调试、发布、授权、依赖及执行状态完整规格。
- 第 4 项：将用户端与管理端关键路径转换为端到端验收用例，再拆分技术实现与 Codex 任务。
### 10.2  待确认的设计细节

| 待确认事项 | 当前建议                         |
| --- |------------------------------|
| 密码要求与找回 | 建议至少 6 字符；不做邮箱找回，由管理员验证身份后重置 |
| Creator 权限 | 默认只能管理自己负责的能力，发布权归 Admin     |
| 待激活账号登录 | 允许正确密码进入“待审核状态页”，不允许其他正式功能   |
| 管理员初始账号 | 受信任初始化创建；不占普通数字注册序列          |
| 游客演示体验 | 以产品介绍/静态预览为主，演示与真实执行严格隔离     |

## 11  最终产品结论

智能助手平台 V1 采用“一个统一用户体系 + 两个工作界面 + 四类 AI 能力 + 一套运行与治理体系”的产品模型。

用户侧完整路径：游客 → 数字账号注册 → 管理员激活 → 登录 → 授权与使用能力 → 保存历史和反馈。

管理侧完整路径：管理员登录 → 用户审核与角色管理 → 能力创建/测试/发布 → 授权治理 → 运行监控与迭代。

下一步以身份、权限和页面信息架构的可用闭环为第一优先级；真实 AI 执行能力是后续必要阶段，不应被继续用演示数据代替。

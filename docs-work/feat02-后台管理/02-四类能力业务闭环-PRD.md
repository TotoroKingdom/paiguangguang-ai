## 1. 目标与产品边界

为 Tool、Skill、MCP、Agent 设计**统一发现、所有权、创建、验证、审核、发布、授权、执行和治理**机制。用户面对的是“可完成任务的能力”，不是四个互不相通的管理页面。

V1 完成标准：Creator 配置一项真实能力并经 Admin 发布，Active 用户能够按权限发现、满足个人授权后执行并取得真实结果；用户与管理员分别看到正确的历史、状态和审计。

### 1.1 定义

| 类型 | 产品定义 | 与其他能力关系 |
|---|---|---|
| **Tool** | 有明确输入输出和执行边界的原子操作 | 可以独立调用或由 Agent 调用 |
| **Skill** | 对任务的指令、方法、资源与依赖的可复用封装 | 加载给 LLM/Agent，不等于独立可执行程序 |
| **MCP Server** | 平台注册的外部工具服务 | 通过发现的工具进入统一 Tool 调用通道 |
| **MCP Connection** | 具体用户对 MCP Server 的连接/授权状态 | 属于用户个人，不能共用其他人的凭据 |
| **Agent** | 模型+提示词+能力依赖的任务执行主体 | 组合 Skill、Tool、MCP Tool 完成任务 |

MCP Server 是平台资源，MCP Connection 是用户个人资源；二者不得混成单一“已连接/未连接”字段。

## 2. 角色、所有权、可见性与权限

### 2.1 资源所有权

- **平台能力**：由 Creator/Admin 维护；需经过管理审批发布，按平台授权给用户使用。
- **个人 Skill**：由 Active 用户上传/编辑并保存在服务端，默认私人；不会无审核进入平台公开目录。
- **个人 MCP Connection**：由 Active 用户以本人身份授权/断开，敏感凭据不显示明文。
- [已确认] V1 普通用户不得注册任意 MCP Server，只能连接平台已批准的 Server；[建议] 同期不开放 User 创建任意外部 Tool 或平台 Agent，防止未验证执行器接入。

### 2.2 四维度+运行就绪

| 维度 | 示例 | 判定意义 |
|---|---|---|
| 所有权 `owner` | platform / user | 谁能修改和管理资源 |
| 发布 `lifecycle` | draft / in_review / published / disabled | 平台治理状态 |
| 可见范围 `visibility` | private / assigned_roles / active_users / public_preview | 谁能发现介绍或目录项 |
| 使用权限 `entitlement` | allowed / denied / approval_required | 谁能发起调用 |
| 运行就绪 `readiness` | ready / auth_required / unavailable / degraded | 此次调用技术上能否执行 |

**发布、可见、授权、执行严格分离。** `published` 只代表版本上线，不自动代表任何用户可用。公开预览只可读安全元数据，不代表游客可执行。

### 2.3 服务端准入判断

对每一次执行都满足：`账户 ACTIVE` ∧ `版本已发布且未被禁用` ∧ `资源可见性/执行权限有效` ∧ `模型与 Tool 就绪` ∧ `依赖版本可用` ∧ `个人 MCP 授权有效` ∧ `预算/风险策略允许`。

不能只依赖前端目录过滤，也不能只根据用户提交的能力 ID 直接执行。管理端权限亦必须作用于 API。

## 3. 平台能力生命周期

### 3.1 流程

`创建草稿 → 配置 → 测试 → 提交审核 → 管理员审核 → 发布不可变版本 → 用户发现 → 授权/启用 → 执行 → 运行反馈 → 版本升级、停用或回滚`

| 状态/动作 | 谁可以做 | 规则 |
|---|---|---|
| 草稿创建/编辑 | Creator（本人）或 Admin | 不影响当前线上版本 |
| 配置测试 | Creator（本人）或 Admin | 测试调用使用受限资源，记录结果及成本 |
| 提交审核 | Creator（本人）或 Admin | 完成必要配置与静态校验 |
| 审核通过/驳回 | Admin | 记录原因、操作者、时间 |
| 发布版本 | Admin | 发布快照不可变；发布前依赖和运行就绪校验 |
| 停用 | Admin | 新调用立即拒绝，运行中关键安全点重新校验 |
| 回滚 | Admin | 恢复某个已验证旧版本的配置，留存可追溯发布事件 |

[建议] 对于单管理员 V1，Admin 可以直接创建并发布，但测试及审计仍不能跳过。发布事务与审计必须原子一致。

### 3.2 版本与依赖

每个发布版本包括元数据、运行配置、依赖清单以及兼容性约束。Agent 的 Tool/Skill/MCP Tool 依赖要绑定具体已发布版本，不依赖不稳定的名称字符串；执行创建 Run 时记录具体解析到的版本。

被依赖的 Tool 紧急停用或用户撤销 MCP 授权后，即使 Agent 仍是已发布状态，也不能继续执行受影响工具。可以给出明确降级方案，但降级必须是已配置的产品行为，**不得回退到模拟响应**。

### 3.3 可见性与启用

- 用户目录只提供安全、可展示的字段：名称、描述、类型、当前状态、必要授权提示。
- 用户只能收藏或启用本人可使用的能力；“已启用”是用户偏好，不替代权限判断。
- 若已发布但尚未就绪，可以展示为“暂不可用/需要授权”，但必须禁用不合法的执行操作。
- 停用后从正式可用目录移除或转为只读历史状态；历史会话仍保留使用时版本快照。

## 4. Tool 产品契约

### 4.1 管理端最小配置

名称、用途、输入 Schema、输出 Schema、执行器类型、超时、调用权限、风险等级、版本变更说明、测试记录。凭据只能保存引用；系统级内置工具由平台维护，外部 HTTP 执行器必须验证目标地址和网络访问策略。

### 4.2 用户端交互

用户在目录中看到能力简介、权限及就绪状态；选择 Tool 后输入合法参数或让 Agent 生成参数。执行前检查用户身份和资源风险：只读低风险可直接执行，写入/删除/外发等高风险动作需显式审批或确认。

### 4.3 验收

至少一个**真实只读 Tool**能够通过后台配置/测试/发布，再由 Active 授权用户成功调用，返回真实结构化结果并产生运行记录；非法参数、权限不足、超时均有可辨别反馈。

## 5. Skill 产品契约

### 5.1 平台 Skill

Creator 创建 Markdown 指令、任务说明、适用条件、必要资源与依赖；测试后提交审核，Admin 发布，用户按授权使用。支持不可变版本和历史查看。

### 5.2 个人 Skill

Active 用户可以导入 Markdown、创建/修改/删除私有 Skill，服务器持久化，跨设备可用；默认所有者本人可见。用户无需走平台发布审批即可启用自己的私有技能，但须遵守平台安全策略。私人 Skill 不得自动具备任意执行工具、访问他人数据的权限。

[建议] 允许用户“申请提交为平台 Skill”，进入平台审核流程；审批通过后发布的是平台托管版本，原私人技能仍归用户所有，避免无意改变归属。

### 5.3 验收

用户 A 导入个人 Skill，重登录后仍可使用；用户 B 不可见也无法通过 ID 调用；同一 Skill 对模型行为产生可确认的真实影响，不是仅在客户端展示 Markdown 文本。

## 6. MCP 产品契约

### 6.1 平台服务接入

Creator/Admin 注册可信 MCP Server，配置传输方式、服务端点、认证要求、访问范围和网络安全策略。必须有**真实的连接检查、工具发现、Schema 校验、工具风险标记和调用审计**；模拟 URL 检查不算连接成功。

[已确认] V1 **普通用户只能连接平台已批准的 MCP Server**，不能自行注册任意 Server 或提交未经批准的网络地址。Creator/Admin 可按治理流程注册和批准服务；远程连接需防范 SSRF、重定向和 DNS 变化，调用遵循最小权限。

### 6.2 个人授权

用户目录看到 MCP 服务是否可用；点击“连接”后进行符合服务实际认证方式的个人授权；前端展示连接状态（未连接/待授权/已连接/失效/失败）。凭据仅供本人授权范围的调用使用，断开连接后立即失效。

MCP Server 的 `tools/list` 发现结果转为统一可调用工具描述，由 Tool Gateway 执行。工具权限与 MCP 服务级权限应分别校验。

### 6.3 验收

至少一个真实 MCP Server 能成功连接并发现工具；用户 A 授权后能够真实调用，用户 B 不共享 A 的凭据；断开/过期后新调用被阻断，历史与审计可见。

## 7. Agent 产品契约

### 7.1 管理端配置

名称、用途、目标用户、模型、System Prompt、Skill/Tool/MCP Tool 依赖、风险与运行预算、执行限制、版本说明。调试时展示真实的模型/工具行为；发布前校验模型和依赖版本、授权策略以及成本边界。

### 7.2 用户侧流程

Active 用户在 Agent 目录发现有权限的 Agent → 查看可用性与需要授权的连接 → 完成授权 → 提交任务 → 获得真实模型输出、工具步骤与执行状态 → 保存历史、反馈或重试。

当依赖缺失时需明确告诉用户：是没有使用权限、MCP 未授权、模型不可用还是 Tool 被停用。禁止将调用失败伪装成工具调用成功。

### 7.3 验收

至少一个**研究助手 Agent**能够加载真实 Skill，调用一个真实 Tool，并按需调用已授权 MCP Tool；后台可查看所用 Agent/依赖版本和最终 Run 状态。

## 8. Run 与可观测性业务契约

### 8.1 状态机

`queued → running → completed` 是主路径；异常终态 `failed / cancelled / timed_out`；非终态还可能 `waiting_authorization / waiting_approval`。每个 Run 有不可变 `run_id`，关联发起者 `user_id`、会话、消息、能力版本、依赖版本、开始/完成时间及可见的错误信息。

“请求准入记录 accepted”不算模型或工具成功运行。真实执行结果需要与准入记录分开。

### 8.2 展示范围

- 用户：只见本人运行及可展示的步骤、最终结果、失败和授权提示。
- Creator：只见本人负责的能力的必要聚合指标及授权的脱敏调试记录，不默认获得用户私人内容。
- Admin：查看全局运行元数据、费用、错误、审计，不默认读取私人正文或第三方凭据。

记录至少含状态、延迟、错误类别、模型/工具调用次数、Token 用量（能获得时）、版本和请求关联。日志对凭据及敏感输入做脱敏。

## 10. 正式目录与演示数据隔离

当前 24 个演示能力和浏览器模拟回复必须从正式调用语义中剥离。V1 约定：

1. 生产正式目录只返回**真正已发布**的能力及其真实运行状态；不可执行不应显示为可调用。
2. 演示资源独立进入“示例/产品介绍”区域，显著标注演示，不写入正式用户运行结果。
3. 不可用时返回明确的错误原因或空状态，不能用 `createMockReply` 或模拟 MCP 连接作为降级。
4. 管理后台的测试结果必须标识真实测试环境，模拟测试不得作为正式发布通过证据。

## 11. 端到端验收（V1 产品门槛）

| 编号 | 场景 | 结果 |
|---|---|---|
| C01 | Creator 建 Tool 草稿并测试 | 真实工具测试成功，有结果和审计 |
| C02 | Admin 审核发布 | 已发布版本不可变，未经审核草稿不可用 |
| C03 | 按角色及授权过滤 | 有权用户可发现，无权用户无法通过 ID 越权调用 |
| C04 | 用户私人 Skill | 跨设备持久化、默认私有、实际影响模型任务 |
| C05 | MCP 服务和用户连接分离 | 用户 A 授权不等于 B 获授权；断开立即阻断 |
| C06 | Agent 依赖 | 发布和执行锁定版本；失效依赖得到可理解提示 |
| C07 | 真实执行 | 至少一条 Agent → Skill → Tool → MCP（必要时）链路取得真实结果 |
| C08 | 完整运行记录 | 真实状态、耗时、错误、用量、用户可见记录与后台审计一致 |
| C09 | 禁用与回滚 | 停用立即拒绝新运行，回滚不破坏旧版本历史 |
| C10 | 无模拟混入生产 | 正式目录和日志不存在假装真实执行的 demo 结果 |

## 12. 待确认决策与范围收敛

1. **平台能力的可见范围**：V1 默认给全部 Active 用户还是仅指定角色？建议默认 Active 用户可浏览简介，执行按权限单独控制。
2. **私人 Skill 升级平台版**：建议允许用户申请提交，管理员审核后复制到平台所有权。
3. **普通用户自定义 MCP Server [已确认]**：V1 不允许；只能连接管理员批准的 MCP Server。
4. **真实工具安全边界**：建议 V1 首批只读 Tool；写操作后续追加确认与风险审批机制。
5. **模型预算**：需确定每用户每日请求、Token、并发和运行时长限制；至少支持管理员全局开关。
6. **Run 是否显示推理过程**：只展示工具调用步骤和结果摘要，不展示模型隐藏推理内容。

## 13. 顺序与集成原则

本 PRD 依赖 `01` 的统一身份和资源所有权约束。计划先打通模型基础调用与一个真实 Tool，再接 MCP Server/用户授权、个人 Skill 加载及 Agent 组合。无论按几期实施，最终验收必须满足业务闭环，不应以四个目录页面可访问作为完成依据。
